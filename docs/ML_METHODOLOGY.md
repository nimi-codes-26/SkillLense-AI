# ML Methodology

This document is derived directly from the conclusion sections of the notebooks in
`ml/notebooks/` and the metadata files in `ml/models/`. If this document and a notebook ever
disagree, the notebook is authoritative — update this document to match it, not the reverse.

## The Single Most Important Rule

> **The skill-category classifier predicts how well a new student resembles clusters that
> K-Means discovered in synthetic data. It does not predict real-world employability, career
> success, or career readiness.** No independent, real-world measurement (job placement,
> mentor assessment, employer feedback) was used to define or validate these categories.

This statement must not be diluted, reworded into an employability claim, or omitted from any
user-facing copy, future documentation, or presentation of this project. It appears, in
equivalent form, in the notebooks, in `ml/models/classifier_info.json`'s `"note"` field, in
`frontend/src/pages/Analysis.jsx`, and in `frontend/src/pages/About.jsx`.

## Dataset

Synthetic, 300 students, 9 features, generated by `ml/generate_synthetic_data.py` from 5
hand-defined archetypes (`high_allround`, `technical_strong_soft_weak`, `average_balanced`,
`developing`, `security_focused`) with normally-distributed noise per feature
(`NOISE_STD = 1.2`) and `RANDOM_SEED = 42`. Full generation notes, column ranges, and
limitations are documented in `ml/data/raw/DATASET_NOTES.md`. The archetype used to generate
each row is saved separately in `generation_reference.csv` and is used only for the author's
own post-hoc sanity-checking — **it must never be used as a feature or target**, since that
would defeat the purpose of discovering categories from the data.

## Stage 1 — EDA (`01_eda.ipynb`)

- Dataset is clean: no missing values, no duplicate rows, all values within valid ranges.
- `coding_skill`, `dsa_skill`, `math_aptitude`, and `projects_count` are moderately-to-strongly
  correlated with each other (0.64–0.75) — expected, since technically-strong archetypes score
  high on all of them together. This is part of the real motivation for using PCA later.
- Only 3 outliers total, across `cgpa` and `math_aptitude` — no outlier-handling step applied.
- Key finding carried into Stage 2: features are on very different scales (skill scores 0–10
  vs. counts 0–5), so standardization is necessary before any distance-based algorithm
  (K-Means, DBSCAN).
- No target, clustering, or classifier work happens in this notebook.

## Stage 2 — Preprocessing (`02_preprocessing_feature_engineering.ipynb`)

- `student_id` is excluded as a feature (arbitrary, sequential, no real relationship to
  skill).
- **Train/test split happens first**, before any scaling — the leakage-safe rule this entire
  pipeline is built around.
- `StandardScaler` is fit **only on the training split** (`X_train`); the test split is only
  ever `.transform()`-ed with those training-derived statistics, mirroring how a genuinely new
  student would be handled in production.
- No target/label, K-Means, DBSCAN, PCA, or classifier is created in this notebook.

## Stage 3 — Clustering / Pseudo-Label Creation (`03_clustering_target_creation.ipynb`)

- K-Means tested for k = 2 through 8 on `X_train_scaled` only, evaluated by inertia and
  silhouette score.
- Silhouette peaked at **k=2 (≈0.31, the global maximum)**, dropped at k=3 (≈0.22), rose again
  to a **local peak at k=4 (≈0.24)**, then declined through k=5–8.
- **k=4 was chosen deliberately over the higher-scoring k=2**, because: it is a genuine local
  peak (better than both k=3 and k=5), the elbow plot supports it as a reasonable stopping
  point, and — the deciding factor — it produces four clusters that are actually
  distinguishable from each other in the original feature space, whereas k=2 would only
  separate "stronger" from "weaker" students and give the product nothing actionable.
- Cluster interpretation (from original, unscaled feature means, inspected **before** any
  names were chosen):

  | Cluster | Profile | Assigned category |
  |---|---|---|
  | 0 | Weakest across every feature | Needs Improvement |
  | 1 | Strong coding/DSA/math/projects, weakest communication | Strong Technical |
  | 2 | Moderate on most features, standout security knowledge | Balanced |
  | 3 | Highest on almost every feature | Strong Overall |

- Cluster 3 was deliberately named **"Strong Overall"** instead of the originally-proposed
  "Balanced", because its actual profile (highest on 7 of 9 features) did not match what
  "balanced" means. This renaming happened only after inspecting the real cluster means — it
  is documented here specifically so it is not "corrected" back to "Balanced" by someone
  unaware of the reasoning.
- These are **pseudo-labels**: produced by an unsupervised algorithm grouping students by
  similarity, followed by human interpretation of the resulting group averages — not by any
  independent, real-world outcome measurement.

Artifacts saved: `scaler.pkl`, `kmeans_model.pkl`, `cluster_category_mapping.json`.

## Stage 4 — DBSCAN Outlier Analysis (`04_dbscan_outlier_analysis.ipynb`) — Exploratory Only

- `eps=2.0`, `min_samples=4`, fit only on `X_train_scaled`.
- Found 2 clusters (209 and 4 students) and flagged **27 of 240 training students (11.2%)**
  as density-based noise/outlier candidates.
- Confirms, from an independent angle, what Stage 3's modest silhouette scores already
  suggested: the four K-Means categories are useful centroid-based groupings, not naturally
  isolated, gap-separated islands of data.
- **No artifacts are saved from this notebook.** A fitted DBSCAN object has no `.predict()`
  for new data, so there is nothing reusable to persist.
- Does not change, feed into, or replace K-Means, the Random Forest classifier, or the career
  alignment engine. It is a standalone exploratory analysis, not part of the live prediction
  path (`ml_service.py` does not use DBSCAN in any form).

## Stage 5 — PCA (`05_pca_visualization.ipynb`) — Exploratory / Visualization Only

- Fit only on `X_train_scaled`.
- PC1 explains **~46.9%** of variance (a general "skill strength" axis, dominated by
  projects/coding/DSA); PC2 adds **~11.5%** (contrasting communication/academic strength
  against security-knowledge/internship-heavy profiles); combined **~58.35%**.
- The resulting 2D visualization, optionally colored by the K-Means pseudo-categories, shows a
  pattern consistent with genuine, loading-supported structure in the data — **not** proof of
  real-world career categories or employability.
- Saved because PCA's `.transform()` is genuinely reusable (e.g., plotting a new student's
  position): `pca_model.pkl`, `pca_info.json`. It does not feed the Random Forest classifier
  or the career alignment engine, and does not replace or validate K-Means.

## Stage 6 — Classification (`06_classification_models.ipynb`)

- Five classifiers trained on `X_train_scaled`, evaluated on `X_test_scaled` against the
  K-Means-derived `skill_category` pseudo-labels: Logistic Regression, K-Nearest Neighbors,
  Decision Tree, Random Forest, Support Vector Machine.
- **SVM scored a perfect 1.00** across all weighted metrics. This was treated as expected
  given how the labels originate (they are cluster-boundary-derived, so a sufficiently
  flexible model can separate them cleanly) — **not** as suspicious or as reason to distrust
  the pipeline — but SVM was still not automatically selected on that basis alone.
- **Random Forest was selected** instead, based on:
  - Weighted accuracy/precision/recall/F1 all **≈0.9667 / 0.9686 / 0.9667 / 0.9665**.
  - No class below 0.90 recall (even class-wise performance).
  - Only **2 misclassifications out of 60 test students**, both explainable by feature overlap
    between adjacent categories.
  - Interpretable feature importances (a benefit SVM does not offer as directly).
- Restated explicitly in the notebook: the classifier's accuracy describes how well it
  reproduces K-Means's clusters for new students, not how accurately it predicts real-world
  career outcomes. **This must never be described as employability prediction, career success
  prediction, or real career-readiness accuracy anywhere this project is presented.**

Artifact saved: `skill_category_classifier.pkl`. Recorded in `classifier_info.json`:
`selected_model = "Random Forest"`, the 9-feature list, target name `skill_category`, the 4
target categories, the evaluation metrics above, and an explicit pseudo-label disclaimer note.

## Live Prediction Path (Backend)

`backend/app/ml_service.py` loads all artifacts once at import time and, for a live request:

1. Orders the incoming profile's 9 fields per the fixed `FEATURES` list (must match training
   order).
2. Applies the already-fitted `scaler.transform()` (never refit).
3. Calls the already-fitted Random Forest classifier's `.predict()` (never refit).
4. The classifier was trained on string labels directly, so its output is already one of the
   4 human-readable category names — no separate ID-to-label mapping step is needed at
   inference time.

`kmeans_model.pkl` is loaded by `ml_service.py` for completeness with the full artifact set
but is **explicitly not used** for live prediction (`_ = kmeans_model` in the source, marking
it as intentionally unused at runtime) — only the trained classifier serves live requests.
Neither DBSCAN nor PCA are loaded or used anywhere in the backend's live request path.

## Career Alignment: A Separate, Non-ML System

The career alignment engine (`backend/app/alignment_service.py`) is **pure Python with no
machine-learning model, no scikit-learn dependency, and no connection to the classifier**. It
is documented in full, including its exact formula and the 5 fixed illustrative career-role
requirement profiles, in [DATA_MODEL.md](DATA_MODEL.md) and [API_REFERENCE.md](API_REFERENCE.md).
It is listed here only to make the boundary explicit: **skill categorization is machine
learning; career alignment is a rule-based calculation.** Keep this distinction intact in any
future feature work or documentation — do not describe career alignment scores as
model-predicted, and do not let the two systems become implicitly coupled in code.
